### 3.1 Step 1：把方案包拷进 `docs/plan/`（10 分钟，纯鼠标）

**为什么要拷进项目里**：Cline 只能看见项目文件夹里的东西。包还躺在「下载」里，它读不到——这跟用什么方式拷无关，鼠标拖进去和敲命令拷进去，结果一模一样。

**只拷 `.md` 和三个文件夹，`.html` / `.pdf` 一开始就不拷。**

包里一共 76 个东西，直接要的只有 **35 个**：32 个 `.md`，加 `content-pack`、`starter-assets`、`submission` 三个文件夹（`submission` 里还夹着 1 个 `.html` 和 1 个 `.pdf`，第 10 步再删）。

剩下的一概不拷：

- **32 个 `.html`**——同一份 Markdown 的网页版。留下来 AI 会读两遍，白花钱；方案包 `PLAN-V4-implementation.md` 里自己就写着"不要读 `.html`"。你自己想看排版好看的版本，直接双击「下载」那个解压文件夹里的 `.html` 就行，不用拷进项目；
- **5 个 `.pdf`**——给老师、家长看的印版，光技术文档就 1.9 MB，提交进 GitHub 会永久留在历史里；
- `build_docs.py`、`build_index.py`、`rename_pdfs.sh`、`__pycache__`——是我们做这几份文档用的工具，跟项目无关。

挑法很简单：**按类型排一下，32 个 `.md` 就并排站在一起了**。

#### 步骤（Windows 11）

1. `Win + E` 打开资源管理器，点左边「**下载**」；
2. 找到 `body-prism-docs.zip`，**右键 → 全部解压缩 → 提取**，会多出一个同名文件夹；
3. 双击进这个解压出来的文件夹，点顶部 **查看 → 排序 → 类型**（或者直接点「类型」这一列的列头）；
4. 这时 `.md` 全排在一起，`.html` 一坨、`.pdf` 一坨。**点第一个 `.md`，按住 `Shift` 点最后一个 `.md`** → 32 个全选中；
5. 按住 `Ctrl` 再点三个文件夹：`content-pack`、`starter-assets`、`submission`。**别点 `__pycache__`**；
6. 看一眼窗口左下角，应该写着「**已选择 35 个项目**」。不是 35 → 重新选，别急着拷；
7. `Ctrl + C`；
8. 在 VSCode 里右键项目根目录 → **在文件资源管理器中显示**，进到 `docs` → 右键空白处 → **新建 → 文件夹** → 打 `plan`；
9. 切到 `docs\plan`，`Ctrl + V` 粘贴；
10. 进 `docs\plan\submission`，删掉里面的 `TECH-DOC.html` 和 `人体棱镜-技术文档.pdf`（1.9 MB，是给老师看的印版）；
11. 检查：`docs\plan` 里要有 **`START-HERE.md`、`PLAN-V4-implementation.md`、`content-pack`、`starter-assets`** 四样，总大小 **4 MB 以内**。

> **懒得挑？** 也可以 `Ctrl + A` 全选粘贴，粘进来再清：选中 `build_docs.py`、`build_index.py`、`__pycache__` 按 `Delete`；搜索框输 `*.html` → `Ctrl + A` → `Delete`；再输 `*.pdf` 删一遍。结果一样，只是多三步。
>
> 条数对不上（不是 35）→ 多半是漏选了 `README.md` 或某个 `UPGRADE-*.md`，回去重挑一次。**「下载」里那份解压文件夹一直在，随便试。**

#### 换成命令也可以（可选，效果完全一样）

不想挑文件就走这条。**看不懂就跳过，鼠标那条路一样快，没有高下之分。**

**前提**：解压出来的文件夹必须叫 `body-prism-docs`（右键 → 重命名）；`docs\plan` 要是空的（里面还有上一次的旧拷贝，先整个删掉再跑）。

**在 VSCode 里按 `` Ctrl + ` `` 开终端**，确认提示符前面的路径是项目根目录（有 `package.json` 那一层，不是桌面），然后整段贴进去回车：

```powershell
$src = "$env:USERPROFILE\Downloads\body-prism-docs"   # 解压出来的文件夹
$dst = "docs\plan"

New-Item -ItemType Directory -Force $dst | Out-Null
Copy-Item "$src\*.md" $dst                            # 只拷根目录的 32 个 .md
Copy-Item "$src\content-pack","$src\starter-assets","$src\submission" $dst -Recurse
Remove-Item "$dst\submission\TECH-DOC.html","$dst\submission\人体棱镜-技术文档.pdf" -ErrorAction SilentlyContinue

(Get-ChildItem -Recurse $dst -File).Count             # 应该输出 58
```

**看到 `58` 就成了**——58 个文件、3.6 MB，`docs\plan` 里照样是那四样。

- 报错 `找不到路径` → `$src` 那行写错了：去「下载」里右键那个文件夹 → 属性，把完整路径复制过来替换掉双引号里的内容（路径里有空格就保留引号）；
- 输出不是 58 → 多半是解压出来的文件夹名字被系统加了 `(1)`，改名成 `body-prism-docs` 再跑一遍；
- 跑完想看拷进来什么：`Get-ChildItem docs\plan | Select-Object -First 10`。

**它只做三件事**：挪 32 个 `.md`、挪三个文件夹、删 `submission` 里那两个印版文件。不删别的、不动 `docs` 以外的地方、不碰 Git。

#### 拷的时候最容易犯的四个错

| 现象 | 说明 | 怎么办 |
|---|---|---|
| 路径变成 `docs/plan/body-prism-docs/PLAN-V4-implementation.md` | 把**整个文件夹**拖进去了，多套了一层 | 进那一层，把里面的东西全选剪出来、粘到 `plan` 下，再把空壳文件夹删掉 |
| 弹窗问「替换 / 跳过 / 保留两者」 | `plan` 里已经有旧版 | 选**替换目标中的文件**。选「保留两者」会生成 `xxx (1).md`，AI 会读错那一份 |
| 找不到「下载」文件夹 | 中文系统多数叫「下载」，也可能在 OneDrive 里 | 资源管理器左栏找「下载」，没有就在地址栏敲 `%USERPROFILE%\Downloads` |
| 解压出一堆散文件和 `__MACOSX` | 正常，不影响 | 只要有那四样就行 |

**做完这一条，先别往下走**：打开 `docs\plan\START-HERE.md`，能看见标题就说明拷对了。打不开（显示乱码或问用什么程序打开）→ 说明拷的是 `.zip` 里的快捷方式，重新解压一次。

#### 三个一定会问的问题

**一、这个 `docs/plan/` 后面要删吗？——不删。**
它是这一周的方案原件：任务卡 T0–T14、11 个器官的内容、`body.glb` 原件、提交材料模板都在里头。
后面每天 AI 干活的提示词里写的都是「`docs/plan/PLAN-V4-implementation.md` 第 5 章 T5」这种路径——
删了，那些提示词就指向空气。**D7 交完作业再考虑删，做的时候一直留着。**

**二、要提交到 GitHub 吗？——要，而且是必须。**
张子昂从头到尾不拷文件，他就是靠 `git pull` 拿到 `docs/plan/` 的（§3.8）。
你不提交，他电脑上就没有这份方案，`PLAN-DAILY.md` 里写的任务卡路径他一个都打不开。
所以 §3.6 那一下 ✓ Commit 是**连 `docs/plan/` 一起提交**，不是只提交代码。

**三、那会不会太大？——不会，因为 `.html` / `.pdf` 一开始就没拷。**
留下来的只有 42 个 `.md`、`content-pack` 里那十几个 `.ts`，加一个 2.7 MB 的 `body.glb`，一共 4 MB 以内。
还有一道保险：§3.6 提交完之后，扫一眼那条提交记录，里面出现 `.html` 或 `.pdf` 说明第 5 步挑错了，删掉再提交一次。

### 3.2 Step 2：开一个分支（2 分钟，点三下）

```text
帮我切到 main、拉最新、再新建分支 chore/upgrade-v4。每一步的终端输出贴给我看。
```

## 4 每天怎么循环（30 分钟固定动作）

一天四个动作，加起来不超过 30 分钟，剩下的时间都在做那一格里的三件事。

### 4.0 先回答一个担心：两个人并行，最后能合上吗？

**能，但前提是"每天合一次"，不是"最后合一次"。这一节很重要，花 5 分钟看完。**

任务**不是**完全独立的——A 写的页面要调用 B 写的接口，A 的红旗组件要用 B 的红旗词表。但两个人分别改动的**文件**接近独立，逐张任务卡对下来，真正两人都会碰的只有 4 个：

| 文件 | 谁改 | 冲突概率 |
|---|---|---|
| `package.json` / `package-lock.json` | A 装 `@google/model-viewer`，B 装 `zod`、`vitest` | **高**，但好解 |
| `README.md` | T1 两人一起，之后只有 B 改 | 中 |
| `ATTRIBUTION.md` | T1 两人一起，T14 由 A 补三维署名 | 低 |
| `docs/**` | B 主导 | 低 |

业务代码是完全分开的（见 §4.6.2 的表）。所以结论是：**可以并行，但必须每天合并，绝不能攒到最后。**

#### 为什么"最后合并"一定会出事

七天下来至少 14 个分支。如果留到 D7 一次性合进 `main`，等于让 14 处改动同时打架，而那天你们已经没有时间排查了。**冲突本身不可怕，可怕的是它爆发在最后一天。**

每天合一次，冲突只发生在"今天"和"昨天"之间，通常就一两行，10 分钟能解完。

#### 真正的风险不是 merge conflict

是**接口对不上**：A 的 `curator-box.tsx` 以为接口返回 `{answer, citations}`，B 实际返回 `{text, sources}`——这在 Git 里**不报冲突**，但页面一跑就崩，而且比冲突难查十倍。

解决办法只有一个：**接口形状提前定死，并且先合进 `main`**。见 §4.6.3。

### 4.1 早上：开工前 3 分钟（全是点鼠标）

```text
① 两人群里各发一句：「D3 · 我做 T5」「D3 · 我做 T8」   ← 这就是"执行前确认"
② 左下角点分支名 → 选 main → 点 ⟳ 同步，把最新代码拉下来
③ 再点分支名 → Create new branch → feat/d3-你的名字
④ 打开 docs/PLAN-DAILY.md，只看今天那一格
```

**顺序不能颠倒**：先回 `main` 拉最新，再从最新处开分支。反着来，你就是在旧代码上开工，晚上合并必撞。

**为什么要发那句话**：两个人改到同一个文件是这一周最大的时间黑洞。一句话 10 秒，能省一小时。

### 4.2 白天：贴提示词（5 分钟 + 干活）

把今天那格的**代码块整块复制**给 Cline。

贴之前做一件事：**读一遍那一格的三件事**。如果三件事里有一件你完全看不懂，先问对方或者看那张卡，不要指望 AI 会替你判断"做得对不对"。

### 4.3 收工：检查 + 提交（10 分钟）

**第一步，让它跑检查**——把这段贴给 Cline：

```text
依次跑 npm run lint、npm run test、npm run build，三条都跑完再一起告诉我结果。
失败的那条把报错原文贴出来，不要自己改代码。
```

（`npm run test` 到 D1 之后才有；它要说"没有这个脚本"，跳过这条就行。）

三条**都通过**才算完成。有一条红，就不算完成——不要"先提交再说"。

**第二步，提交（点鼠标）**：

1. VSCode 左侧「源代码管理」；
2. 输入框写：`feat(chain): D3 影响链页面骨架（T5）`；
3. **✓ Commit** → 弹窗选 **Yes**（暂存全部）；
4. **Sync Changes** 推上去。

**第三步，GitHub 上开 PR**，描述写三行：今天做了哪张卡 / 改了哪些文件 / 怎么验证的。

> 手敲也完全可以，三条命令而已：`npm run lint`、`npm run test`、`npm run build`，然后
> `git add -A && git commit -m "..." && git push`。**和上面的点击是一回事，选你顺手的。**

### 4.4 收工后：让它重排计划（5 分钟）

把下面这一段**整块**贴给 Cline，只改第 3 行——把今天真实做完到哪写清楚：

```text
【同步计划】读 docs/PLAN-DAILY.md，按今天的实际进度更新它。

今天的情况：（自己填一行。例：T3 做完了；T4 只写完 2 个函数，测试还没写）

更新规则：
1. 今天那格：状态改成「✅ 已完成」或「⚠️ 部分完成」，后面补一句实际做到哪
2. 没做完的：整条顺延到明天的同一列。不要删、不要合并、不要偷偷降级成"可选"
3. 明天及以后：按剩余天数重排。时间不够时按这个顺序砍：T11 别名搜索 → T14 三维入口
   → T13 首屏叙事 → 缓存优化。每砍一项，必须在「更新记录」里写一行"砍掉 X，理由 Y"
4. 守恒检查：T0–T14 每一张卡，要么出现在某一天，要么被显式标记"已砍（理由）"。
   不许有卡片凭空消失。检查完把结论写在更新记录里
5. 重写"明天"那两格的提示词块，依据今天的真实产出
   （比如接口签名已经定了，就把真的签名写进提示词，别留占位符）
6. 顶部状态行、更新记录表同步更新
7. 不要动 <!-- 人工备注开始 --> 到 <!-- 人工备注结束 --> 之间的内容
8. 不要改 docs/plan/ 里的方案包原件

做完用 5 行以内说：改了哪几处、明天两个人各做什么。
```

它会更新 `PLAN-DAILY.md`：今天打勾、没做完的顺延、明天及以后重排。

**你只需要检查一件事**：T0–T14 数一遍，是不是 15 张都还在。少了就问它"哪张卡被删了，理由是什么"。

### 4.5 今天的完成度，三档自评

| 档 | 判断标准 | 明天怎么做 |
|---|---|---|
| **完成** | 收工命令全绿，PR 已开 | 正常往下 |
| **做了大半** | 主功能在，但测试/边界没做 | 顺延到明天，后天相应压缩 |
| **没动** | 连分支都没开 | **当天晚上就在群里说**，不要憋到第三天 |

> 连着两天"没动"，就要动 §8 的第一级止损：砍功能，不要砍日期。

### 4.6 两个人并行，怎么保证最后能合上

#### 4.6.1 先定一条铁律：分支不过夜

**每天开分支，每天合回 `main`。** 一个 PR 如果过了夜还没合，第二天早上第一件事就是先把它合掉，再开新的。

原因很直接：两个分支放两天，冲突从"一两行"变成"一个文件的两半"；放七天，就是**两个人各写了一个版本**，那时要的不是解决冲突，而是挑一个重写。

#### 4.6.2 文件所有权表（照这个走，冲突少 90%）

| 文件 / 目录 | 谁的 | 说明 |
|---|---|---|
| `src/app/page.tsx` | **A** | T13 改首屏、T14 加三维入口，都是 A |
| `src/app/chain/page.tsx` | **A** | T5 建、T6/T7/T9 往里加 |
| `src/components/` 下所有 `.tsx` | **A** | 包括 `chain-canvas`、`evidence-panel`、`red-flag-gate`、`curator-box`、`organ-viewer` |
| `src/lib/chain.ts`、`chain.test.ts` | **A** | T4 的三个纯函数 |
| `src/data/anatomy-hotspots.ts` | **A** | 从方案包复制，一个数不改 |
| `src/content/**` | **B** | 器官内容、影响链数据，A 一行都不许改 |
| `src/lib/schema.ts`、`validate-content.ts`、`red-flag.ts` | **B** | |
| `src/app/api/curator/route.ts` | **B** | A 只调用，不修改 |
| `docs/**`、`README.md`、`ATTRIBUTION.md` | **B** | 例外：T14 的三维署名由 A 补，改完立刻合 |
| `.clinerules` | **T1 建完即冻结** | 要改先在群里说，两分钟的事 |
| `package.json` `package-lock.json` | **谁装依赖谁改** | A 只装 `@google/model-viewer`；B 只装 `zod`、`vitest` |

**规则只有一句：一个文件，同一时间只有一个人在改。** 要改对方的文件，先在群里说一句"我要动 X"，或者直接请他改。

#### 4.6.3 三个"合同点"：开写之前必须定死

| 合同 | 谁定 | 谁用 | 定义在哪 | 必须什么时候合进 `main` |
|---|---|---|---|---|
| 影响链的数据形状（节点、边、证据等级） | B（T3） | A（T4、T5、T6） | **P2 §4.1** | **D2 上午** |
| AI 接口的请求 / 响应形状 | B（T8） | A（T9） | **P2 §4.3** | **D4 上午** |
| 红旗词表 | 两人一起 | A（T7）、B（T8） | **P2 · T7** | **D4 上午** |

**做法：先合"合同"，再合"实现"。**

不用等对方全做完。B 可以先把类型定义 + 空函数体提交进 `main`：

```ts
export async function askCurator(req: CuratorRequest): Promise<CuratorResponse> {
  throw new Error("TODO: T8 实现中");
}
```

A 从 `main` 拉下来，照着类型就能把界面写完，调用时接口返回 `TODO` 也不影响 A 先把页面接起来。等 B 实现完，A 只改一次 `git pull`，什么都不用动。

> **为什么这套方案能并行**：P2 §4.1 和 §4.3 已经把两份合同的字段写死了。你们**不是各自猜对方要什么，是照着同一张表写**。这两节的字段谁都不许"顺手改一下"——改接口形状的成本，比改实现高十倍。

#### 4.6.4 真撞上了怎么解（照做，别慌）

先把你分支上落后的部分补上——**不用敲命令**：

1. 左下角点分支名 → 先切 `main` → 点 ⟳ 同步；
2. 再切回你自己的分支；
3. 按 `F1` 打开命令面板 → 输入 `merge` → 选 **Git: Merge Branch...** → 选 `main`。

撞上的时候，VSCode 会给你两处提示：左侧「源代码管理」里多出一组带 `!` 的**合并更改**；打开的文件里出现这样的块：

```text
<<<<<<< HEAD
这是我们分支上的写法
=======
这是 main 上的写法
>>>>>>> main
```

（`HEAD` 是你这边，`main` 是对方那边。）**别急着点上面那排小按钮**，先做第 1 步：

1. **先在群里问对方**："`src/xxx.ts` 你改了哪几行？"（30 秒，比你自己猜快十倍）；
2. 打开冲突文件，一段一段看：**两边都要，点 `Accept Both Changes`**；只能留一个，按对方说的选 `Accept Current`（你）或 `Accept Incoming`（对方）；
3. 确认文件里**再没有 `<<<<<<<`、`=======`、`>>>>>>>` 这三种行**了（有就手工删掉，留着必报语法错）；
4. 左侧「源代码管理」里点这个文件的 **+**，把它标记为已解决；
5. 让它跑一遍 `npm run build`，必须过；
6. **✓ Commit** → **Sync Changes**，合并就完成了。

> 手敲的等价写法：`git merge main` → 改文件 → `git add 冲突文件` → `git commit` → `git push`。

**任何时候都不许做这四件事**：

| ❌ | 后果 |
|---|---|
| `git push --force` | 把对方的提交冲掉，且找不回来 |
| `git reset --hard` | 把你自己没提交的活儿扔掉 |
| `git checkout --ours .` 一把梭 | 静默丢掉对方整份改动，能编译但功能没了 |
| 冲突没解完就 `git commit` | 把 `<<<<<<<` 提交上去，CI 直接红 |

#### 4.6.5 一个数字帮你判断要不要紧张

| 合并时机 | 冲突的量 | 解决耗时 | 风险 |
|---|---|---|---|
| 当天合（推荐） | 1~2 处，几行 | 10 分钟 | 低，而且当天就知道撞了 |
| 隔一天合 | 1 个文件整块 | 30 分钟 | 中 |
| 攒到 D7 合 | 多个文件、两个版本并存 | **半天到一天，且可能合不完** | **高，且那天没有余量** |

**所以：并行开发没问题，"最后合并"才是那个会把项目弄没的决定。**

## 5 跟 Cline 说话的五个句式

**核心原则：一次只让它做一件事，且要求它先复述再动手。**

### 5.1 开一个新任务（正规句式）

```text
【任务】P2 · T5，/chain 页面骨架
【先读】只读这两个文件：src/lib/impact-graph.ts（类型部分）、src/app/page.tsx
【要做】1. 新建 src/app/chain/page.tsx，读 URL 的 ?organ= 参数
       2. 显示该器官的一跳邻居列表（先用 impactEdges 硬过滤，不做图渲染）
       3. 器官不存在时显示 404 提示，不要崩
【不要】不要装任何新依赖；不要改 src/content 下的内容；不要动首页
【完成】跑 npm run build，把结果贴出来，并列出改动的文件
```

**为什么后面三行比前面重要**：AI 的失败方式不是"做不到"，而是"多做"。把边界写死，你就能一眼看出它有没有越界。

### 5.2 报错（不要说"它坏了"）

```text
【报错】下面是完整报错，先不要改代码。
1. 复述你看到的错误信息和它指的文件行号
2. 给两个最可能的原因，按可能性排序
3. 告诉我每个原因该怎么验证（跑哪条命令、看哪一行）
等我确认后再改。
```

**关键动作**：从终端**整段复制**报错，包括最后几行 `at ...`。不要自己总结成"它报错了"——总结会把定位信息弄丢，AI 只能瞎猜。

### 5.3 它改多了 / 改歪了（立刻收窄）

```text
停。先 git diff --stat 告诉我你改了哪些文件。
把 <A> 和 <B> 还原（git checkout -- A B），只保留 <C>。
然后重新只做这一件事：<一句话>。
```

**不要做的事**：不要接着叫它"修一下"。在错误的基础上修，只会越改越远。**先回滚到一个干净状态，再重做一次。**

### 5.4 它说"完成了"，但你没看见效果（验收三问）

```text
你说完成了，但我看到的是：<现象，比如页面还是白的 / 按钮点了没反应>。
先不要改代码，按顺序回答：
1. 你改了哪个文件的哪几行？
2. 这个效果应该由哪一行代码产生？
3. 要验证它生效，我应该打开哪个 URL、看到什么？
```

三个问题它答不圆，就是没做完。**AI 的"完成"和你的"完成"不是一回事**，只有第 3 问能对齐。

### 5.5 三次法则：它开始反复试错

```text
你已经试了三次还没解决。停下来，不要再改。
把你试过的三次、每次的结果、你认为最可能的根因写出来。
然后告诉我：该查哪份文档的哪一节，或者该问谁。
```

**为什么要有这一条**：AI 陷入循环时，每一轮都在消耗你的时间，而且会开始"为了让报错消失"而删代码。**三次就是止损线**，超过就换人（换人 = 问对方，或者你自己看文档）。

### 5.6 四句话，绝对不要对 AI 说

| ❌ 不要说 | 因为 | ✅ 改成 |
|---|---|---|
| 「把整个项目检查一遍」 | 会读爆上下文，然后开始编 | 「只读 X 和 Y 两个文件」 |
| 「照着文档全部实现」 | 文档 1.5 MB，它读不完 | 「只做 T5 这一张卡」 |
| 「你觉得怎么做更好？」 | 会推翻已经定好的方案，浪费两天 | 「按 D07 §5 的组件表做」 |
| 「顺便把样式也调一下」 | 一次改两件事，出错分不清哪件 | 分成两轮问 |

### 每天四步

| 步 | 早上（3 分钟） | 晚上（10 分钟） |
|---|---|---|
| **1** | 群里发：「D? · 我做 T?」 | 贴给 AI：「依次跑 lint、test、build，结果原样贴我」 |
| **2** | 左下角分支名 → `main` → 点 ⟳ 同步 | 三条全绿才算完成；有一条红就别提交 |
| **3** | 左下角 → Create new branch → `feat/d?-名字` | 源代码管理 → 写 `feat(...)` → ✓ Commit → Sync |
| **4** | 打开 `docs/PLAN-DAILY.md`，只看今天那格 | GitHub → Create PR → 对方 Approve → Squash merge → **删分支** |

### 每天只贴三句话

| 什么时候 | 直接抄 |
|---|---|
| **开始干活** | 把 `PLAN-DAILY.md` 今天那格的代码块**整块**复制粘贴，回车 |
| **它说完成了** | 「你说完成了。跑一遍 `npm run build`，把最后几行输出原样贴出来，不要总结。」 |
| **收工** | 贴 §4.4 那一整段「同步计划」提示词，只改第 3 行「今天的情况」 |

### 四条铁律

1. **一次只让 AI 做一件事**——所有翻车都来自"顺便把别的也改一下"。
2. **它说"完成"不算**——命令绿了、页面对了才算。
3. **同一个问题试三次还不行** → 停下来问人，别跟 AI 互相说服。
4. **分支不过夜**——当天开的 PR 当天合。

### 三件绝对不能做

| ❌ | 后果 |
|---|---|
| `git push --force` | 把对方的提交冲掉，找不回来 |
| `git reset --hard` | 把你自己没提交的活儿全扔掉 |
| 冲突攒到 D7 再合 | 那天你一定没有时间解 |

### 卡住先问自己四句

报错原文贴全了吗？　·　VSCode 打开的是 `body-prism` 吗？　·　F12 Console 看了吗？　·　`.env.local` 改完**重启**了吗？

> 四句都"是"还卡着 → 查 §7 那张表（按现象找，20 条），或者直接问对方。

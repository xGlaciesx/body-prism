## 摘要

人们获取身体知识的方式正在改变：从"搜索症状"转向"直接问 AI"。但通用大模型给出的是**结论**，不是**推理**——它不说明这句话来自教科书还是营销号，也不区分共识与假说。

「人体棱镜」针对这一点，把身体知识组织成一张**带证据等级的影响图谱**：选一个器官，能看到它受谁影响、影响谁、出问题可能出现什么表现；每一条关系都标着 A/B/C/D 证据等级与来源。在此之上，**AI 只能在图上走**——回答以"链"的形式呈现，每一段都可点开核对，链上没有依据的地方就明说没有。

在这个框架里，同一个器官还提供三种并行的读法——**结构之镜**（解剖事实）、**关系之镜**（系统交互）、**信息之镜**（概念类比）——作为叙述方式，而不是并列的三篇文章。

技术上，项目采用 Next.js App Router + TypeScript + Tailwind CSS，内容以结构化 TypeScript 数据维护，用 Zod 做构建期与运行时双重校验；AI 策展人通过服务端 Route Handler 调用 DeepSeek（OpenAI 兼容接口），只向模型提供当前器官的 claims 与 sources，强制 JSON 输出并做引用存在性校验，失败时回退到预生成答案。

本文档依次说明项目概述、需求分析、系统架构、AI 技术方案、核心功能实现、测试与部署、总结与展望，并单列技术创新点与应用创新点。

## 1 项目概述

### 1.1 背景

身体类内容在中文互联网上存在三个突出问题，而且因为 AI 的普及被同时放大了：

1. **信息密度高但可信度不可见**：读者无法判断一句话来自教科书、单篇研究，还是营销号；
2. **不同知识体系被混写**：解剖学事实、传统理论、工程类比常被放进同一段话，读者误以为它们同等可靠；
3. **AI 问答缺乏溯源，且缺少推理**：模型给出的回答看似专业，但既不能核对来源，也看不到它是怎么从 A 推到 B 的；用户拿到的是结论，不是可以自己走的路径。

「人体棱镜」针对这三点，把**证据等级**做成产品的第一等公民：不是文末放一排参考文献，而是每一条结论、每一条关系旁边就有一个 A/B/C/D 徽章，点开即可看到来源与限定条件。

**为什么是"链"而不是"问答"**：一句"肾不好会气短"如果只是结论，读者只能选择信或不信；如果它是"肾 → 血容量与血压 → 心脏后负荷 → 肺淤血 → 气短"这样一条链，读者可以逐段检查，也可以追问其中任意一段。**把结论变成可检查的路径，是我们对"可信 AI"的具体回答。**

### 1.2 项目目标

| 目标 | 可验证的标准 |
|---|---|
| 让可信度可见 | 每条 claim 必须有 `evidenceLevel` 与至少一个 `sourceId` |
| 让三种读法不混淆 | 信息论内容必须标"概念类比"；传统理论必须标"传统理论" |
| 让 AI 回答可核对 | 回答中的每个引用必须存在于当前器官的 `sources` |
| 让演示不依赖网络 | 模型不可用时，问答抽屉回退到预生成答案 |
| 守住医学边界 | 不诊断、不开药、不给剂量；红旗症状先建议就医 |

### 1.3 目标用户与使用场景

| 用户 | 场景 | 需求 |
|---|---|---|
| 大学生（非医学专业） | 准备课堂展示、写通识课作业 | 快速获得可靠、可引用的器官知识 |
| 年轻职场人 | 体检报告出现陌生名词后自行了解 | 区分"事实"与"营销话术" |
| 医学生 / 科普作者 | 核对常见说法 | 快速定位来源与证据等级 |
| 评委 / 教师 | 评估内容可靠性 | 一眼看出证据分级规则是否被遵守 |

### 1.4 范围边界与伦理原则

**做**：**11 个器官**（五脏六腑缺三焦：心、脑、肺、肝、肾、胃、脾、胆、小肠、大肠、膀胱）的三镜内容、误区纠正、带引用的 AI 问答、方法说明。

**不做**：用户注册、支付、诊断建议、处方与剂量、真实患者数据、公开上传内容。

**伦理原则**：

1. 不做诊断、不开药、不给剂量；急症红旗先建议就医；
2. 中医内容标"传统理论，非现代医学共识"；
3. 信息论内容标"概念类比"，不写成机制结论；
4. 不把假说写成共识，证据等级 A/B/C/D 必须标清；
5. 不复制商业图库、教材插图与论文图片。

## 2 需求分析

### 2.1 用户需求拆解

```text
"我想了解这个器官"
   ├─ 它长什么样            → 结构之镜
   ├─ 它和身体其他部分什么关系 → 关系之镜

   ├─ 这条说法可信吗          → 证据徽章 + 来源

```

## 3 系统架构设计

### 3.1 总体架构

```text
┌──────────────────────────────────────────────────────────┐
│ 表现层  React 19 / Next.js App Router / Tailwind CSS      │
│ 首页 · 探索 · 器官详情 · 方法 · 关于 · AI 抽屉            │
└──────────────────────┬───────────────────────────────────┘
                       │ Server Components（默认）
                       │ Client Components（交互：标签、抽屉、3D）
┌──────────────────────▼───────────────────────────────────┐
│ 领域层                                                    │
│  ├─ content/organs/*.ts   11 个器官的结构化内容            │
│  ├─ lib/schema.ts         Zod schema（类型 + 运行时校验）   │
│  ├─ lib/content.ts        读取、索引、引用完整性检查        │
│  └─ lib/curator.ts        上下文构造、引用过滤、降级        │
└──────────────────────┬───────────────────────────────────┘
                       │ Route Handler（仅服务端）
┌──────────────────────▼───────────────────────────────────┐
│ 外部服务  DeepSeek Chat Completions（OpenAI 兼容）          │
└──────────────────────────────────────────────────────────┘
```

### 3.2 技术选型与理由

| 层 | 选择 | 理由 | 放弃的方案 |
|---|---|---|---|
| 框架 | Next.js 15 App Router | SSR 利于分享与 SEO；Route Handler 天然隔离密钥；Vercel 零配置部署 | 纯 Vite SPA（密钥需另建后端） |
| 语言 | TypeScript | 内容字段多，类型可防错配 | JavaScript |
| 样式 | Tailwind CSS | 设计令牌集中，避免样式漂移 | CSS Modules（重复多） |
| 校验 | Zod | 同一份 schema 推导 TS 类型并做运行时校验 | 手写 if 校验 |
| 3D | `<model-viewer>`（Google Web Component），**已采用** | 只做"转一转 + 点热点"，一个 HTML 标签就够；在 `useEffect` 里动态 import，不进首屏 JS；模型加解码器合计约 2.8 MB，按需加载 | React Three Fiber（要自己搭场景、相机、材质，一周做不完） |
| 模型 | DeepSeek（OpenAI 兼容） | 中文稳定、成本低、接口兼容 OpenAI SDK | 闭源高价模型（预算不符） |
| 部署 | Vercel | 与 Next.js 原生集成，环境变量托管 | 自建服务器（维护成本高） |

### 3.3 数据模型

内容以 TypeScript 对象维护，由 Zod 约束。核心实体：

```text
OrganContent
 ├─ id / slug / nameCn / nameEn / system
 ├─ summary / readingMinutes
 ├─ camera            3D 相机初始位姿
 ├─ lenses             三张镜片：structure / relationship / information
 │    └─ LensCard { title, body, claimIds[], visual }
 ├─ claims[]           Claim { id, lens, text, evidenceLevel, sourceIds[], caveat? }
 ├─ misconceptions[]   { myth, correction, sourceIds[] }
 ├─ followups[]        3–5 个可继续追问的问题
 ├─ sources[]          Source { id, title, authors?, year, type, level, url?, doi?, note? }
 └─ related[]          相关器官 slug
```

**引用完整性**是本模型的关键约束：

- `lenses.*.claimIds` 中的每个 id 必须存在于 `claims`；
- `claims[].sourceIds` 与 `misconceptions[].sourceIds` 中的每个 id 必须存在于 `sources`；
- 校验在构建期执行，任何悬空引用都会让 `npm run build` 失败。

### 3.3.1 影响图谱（ImpactGraph）

在三镜内容之外，另有一张跨器官的有向图，用于回答"它受谁影响、影响谁、出问题可能有什么表现"：

```text
ImpactNode
 ├─ id                 "organ:kidney" / "fn:blood-pressure" / "man:edema"
 ├─ kind               organ | function | manifestation
 ├─ nameCn
 ├─ organSlug?         organ 节点跳转到 /organ/[slug]
 └─ redFlag?           manifestation 专用：急症表现

ImpactEdge
 ├─ from / to          节点 id
 ├─ relation           affects（影响）| modulates（调节）| manifests（表现）
 ├─ mechanism          一句话机制：说清"怎么过去的"
 ├─ evidenceLevel      A | B | C | D —— 是**边**的属性，不是文章的属性
 ├─ sourceIds[]        必须指向已有 organ 内容包中的 SRC-* 编号
 └─ caveat             必填：关联≠因果 / 个体差异
```

三处与普通知识图谱不同的设计：

1. **证据等级挂在边上**，而不是挂在整体介绍上——"肾影响血压"是 A 级，"肝影响脑"只是 B 级，强弱差异必须逐条可见；
2. **`caveat` 为必填**，把"关联不等于因果"写进数据结构，而不是写进页脚免责声明；
3. **`relation` 三分**，`affects` / `modulates` / `manifests` 不混用，避免把相关关系表述成因果。

图谱与三镜内容共享同一套 `SRC-*` 来源编号，因此**引用校验只需实现一次**，同时覆盖两套数据。

### 3.4 内容校验流程

```text
作者编写 organs/*.ts
        │
        ▼
Zod schema 解析（字段、枚举、长度）
        │
        ▼
引用完整性检查（claimIds / sourceIds 是否存在）
        │
        ├─ 失败 → 构建报错，阻止合并
        └─ 通过 → 静态生成页面
```

选择"构建期失败"而不是"运行时警告"，是为了让内容错误在合并前暴露，而不是等评委点开页面才发现。

### 3.5 部署架构

```text
GitHub main ──► Vercel Build（npm ci → next build）
                     │
                     ├─ 静态页面（器官内容在构建期生成）
                     └─ /api/curator（Node 运行时，读取环境变量）
                              │
                              └─► api.deepseek.com
```

- 内容页在构建期静态化，访问不触发模型调用；
- 只有用户主动提问才调用模型，成本可控；
- 环境变量只在服务端运行时可见，构建产物中不含密钥。

### 3.6 安全设计

| 风险 | 措施 |
|---|---|
| 密钥泄露 | 仅 `process.env` 服务端读取；不加 `NEXT_PUBLIC_`；`.env.local` 在 `.gitignore` |
| 提示词注入 | 用户问题只作为 `user` 消息；系统提示固定；不把用户输入拼进系统角色 |
| 引用造假 | 模型返回的 `sourceId` 必须存在于当前器官；不存在则丢弃该引用，引用为空则整条回退 |
| 越权访问 | 无登录、无用户数据；管理操作不暴露在公网 |
| 内容越界 | 红旗关键词前置拦截；医学声明由临床医学成员审核 |

## 4 AI 技术方案

### 4.1 选型理由

| 维度 | DeepSeek | 说明 |
|---|---|---|
| 中文能力 | 强 | 医学科普语境下表达稳定，术语错误率低 |
| 接口兼容性 | OpenAI 兼容 | 用原生 fetch 调用，不引入额外 SDK |
| 成本 | 低 | 单次问答上下文约 2–4k tokens，且 30 分钟缓存复用 |
| 结构化输出 | 支持 response_format | 强制 JSON，便于程序校验 |
| 数据合规 | 可关闭训练使用 | 按平台条款配置 |

**不选更大闭源模型的原因**：回答质量瓶颈不在模型规模，而在**上下文供给**与**逐边校验**。把当前器官的一阶子图精准投喂、对输出逐边回溯，比换更贵的模型更有效。

### 4.2 集成方式

```text
浏览器（Client Component）
   │ POST /api/curator { organSlug, question }
   ▼
Route Handler（服务端，原生 fetch，无 OpenAI SDK）
   ├─ Zod 校验请求体
   ├─ 红旗本地判定 needUrgentHelp() → 命中直接返回就医提示，不调模型
   ├─ getImpactSubgraph() 取该器官一阶子图
   ├─ 查缓存 cacheGet() → 命中直接返回
   ├─ 调 DeepSeek（buildSubgraphText 构造上下文）
   ├─ verifyAiOutput() 逐边校验 path 与 sourceIds
   └─ 任何失败 → buildFallbackPayload() + cacheSet() + logCurator()
   ▼
返回 { mode: "ai"|"fallback", answer, path[], sourceIds[], notice }
```

关键点：

1. **密钥不出服务端**：只在 Route Handler 读 `process.env.DEEPSEEK_API_KEY`，浏览器拿不到；
2. **红旗在模型之前**：`needUrgentHelp` 是本地规则，急症关键词根本不进入推理流程；
3. **图约束生成**：只把该器官的一阶子图给模型，模型走不出图外；
4. **失败可演示**：无 key / 超时 / 限流 / 校验失败都回退预生成答案，不 500 白屏。

### 4.3 图约束生成（Graph-constrained generation）

这是本项目 AI 方案的核心：**不给模型整个知识库，只给它当前器官的一张"地图"，并要求它把走过的路画出来。**

服务端用 getImpactSubgraph("organ:" + organSlug) 取出该器官的一阶子图（入边 + 出边 + 邻居节点），再用 buildSubgraphText() 把它压成给模型看的紧凑文本。关键设计是**每条边同时给出中文名和英文 id**：

```text
- 心脏(organ:heart) →（affects）→ 血压(fn:blood-pressure)｜心输出量是血压的决定因素之一……｜证据 A｜来源 SRC-HEART-002
- 自主神经(fn:autonomic) →（modulates）→ 心脏(organ:heart)｜交感神经加快心率与增强收缩力……｜证据 A｜来源 SRC-HEART-002
```

为什么必须给英文 id：模型输出 `path` 时要逐字抄写 `from`/`to` 的节点 id，如果上下文里只有中文名，模型无法返回正确 id，path 校验必然失败（这是实际踩过的坑）。

模型返回后，服务端逐条检查 `path` 中的边是否存在于子图。只要有一条边不在图里，就说明模型走到了图外，该段回答作废。**这就是"图谱约束"：不是提示模型别乱说，而是让它乱说之后必然被发现。**

### 4.4 输出约束与逐边校验

模型输出目标结构（由 `CuratorAiSchema` 用 Zod 定义）：

```json
{
  "answer": "运动时自主神经对心脏的调节发生变化……",
  "path": [{ "from": "fn:autonomic", "to": "organ:heart" }, { "from": "organ:heart", "to": "fn:blood-pressure" }],
  "sourceIds": ["SRC-HEART-002", "SRC-BRAIN-002"]
}
```

服务端用 `verifyAiOutput()` 按顺序校验，任何一步不过整条回退：

1. Zod `safeParse` 解析 JSON（先剥掉可能包裹的 ```json 代码块）；
2. `answer` 去空格后长度 20–600 字；
3. `verifyPath()`：path 长度 1–3、逐条首尾相接成连续链、每条边都在本次子图里（from+to 精确匹配，不看方向猜）；
4. `verifySourceIds()`：sourceIds 非空，且每个 id 都来自 path 各边来源的并集。

**为什么逐边校验**：模型可能"编"一条看起来合理的边或一个 sourceId。程序只认子图里真实存在的边、真实存在的来源，这是"可溯源"的工程保证——不是靠提示词请求它诚实，而是让它乱说之后必然被拦截。

### 4.5 降级策略

| 失败类型 | 处理 |
|---|---|
| 未配置 key | `console.warn` 一行，直接 fallback |
| 网络超时（8s） | fallback，不重试 |
| 429 限流 | 识别错误中的 429，直接 fallback，不重试 |
| JSON 解析 / Zod 校验失败 | fallback |
| path 或 sourceIds 校验失败 | fallback |
| 命中红旗关键词 | `needUrgentHelp` 本地判定，不调模型，返回就医提示（不缓存） |

预生成答案覆盖 12 个高频问题（每个器官 2 个），由 `pickFallback()` 按关键词命中；未命中则返回通用引导。演示现场即使断网，问答抽屉仍可完整展示。

### 4.6 提示词设计

系统提示词（`SYSTEM_PROMPT` 常量）的核心约束：

```text
你是「棱镜策展人」。你只能使用下面给出的影响链，不能引入链上没有的器官、功能或表现。
规则：
1. 只解释"这条链怎么走"，不判断提问者是否患病，不给诊断、建议、药物或剂量。
2. 回答 3–5 句中文，每一句都要能对应到下面某一条边。
3. 只输出 JSON：{"answer": "...", "path": [{"from":"...","to":"..."}], "sourceIds":["..."]}
4. path 中的 from/to 必须逐字取自每条边「中文名(英文id)」里的英文 id；最多 3 条边，首尾相接。
5. sourceIds 只能取自这些边标注的来源。
6. 与这些边无关的问题，返回 path:[] 和 sourceIds:[]。
可用链（每行一条边）：
{{SUBGRAPH}}
```

设计要点：**角色限定**（策展人非医生）、**材料限定**（只给子图）、**格式限定**（强制 JSON）、**路径限定**（id 逐字取自上下文）。

### 4.7 缓存、日志与成本优化

| 手段 | 实现 | 效果 |
|---|---|---|
| 结果缓存 | `cacheKey`/`cacheGet`/`cacheSet`：内存 Map，TTL 30 分钟、上限 200 条淘汰最旧 | 同问题 30 分钟内命中缓存，省一次模型调用 |
| 缓存键脱敏 | key = organSlug + hash(question)，不存提问原文 | 避免在内存留存用户提问 |
| 一行 JSON 日志 | `logCurator`：只记 organSlug / mode / cacheHit / 耗时 / 失败原因 | 可观测，且不泄露 question、key、模型原始输出 |
| 内容页静态化 | 浏览不调模型 | 零推理成本 |
| 只投喂当前器官子图 | `getImpactSubgraph` | 上下文 2–4k tokens |
| 超时不重试 | 8s 超时，429 直降 | 避免尾延迟与限流雪崩 |

> 具体 token 消耗与费用以交付版本实测为准，本文档不预设虚构数字。

### 4.8 安全与合规

1. **红旗本地前置**：`needUrgentHelp()` 用 `RED_FLAG_KEYWORDS`（胸痛、呼吸困难、意识不清、抽搐、大出血、剧烈头痛等）在调用模型前拦截，模型不参与红旗判定；
2. **拒绝诊断**：系统提示明确禁止诊断、用药、剂量；
3. **不收集个人数据**：不要求登录、不存对话；日志不记 question 原文；
4. **密钥不出服务端**：只从 `process.env` 读，不加 `NEXT_PUBLIC_` 前缀，日志不打印 key；
5. **可审计**：每次回答返回 `mode` 与 `sourceIds`/`path`，便于复查。

### 4.9 评估方法

采用人工评分（1–5 分），每题由两名成员独立打分：

| 维度 | 说明 |
|---|---|
| 事实一致性 | 回答是否与所引边/claim 一致 |
| 引用有效性 | sourceIds 是否真的来自 path 涉及边 |
| 边界遵守 | 是否拒绝诊断/用药、红旗是否本地拦截 |
| 表达克制 | 是否避免夸张与绝对化 |
| 可读性 | 是否 3–5 句说清 |

评估集：每个器官 2 题 + 4 个红旗问题，共 16 题。低于 4 分的回答进入提示词迭代。

## 5 核心功能实现

### 5.1 首页

- 首屏一句话主张 + 三张镜片卡片；
- 11 个器官入口（核心 6 个在前，扩展 5 个折叠）；
- 页脚固定免责声明与方法页入口。

实现要点：首页为 Server Component，器官列表在构建期生成，无客户端请求。

### 5.2 器官详情与三镜切换

```text
/organ/[slug]
 ├─ 头部：名称、系统、阅读时长、一句话摘要
 ├─ 镜片标签：结构 / 关系 / 信息
 ├─ 当前镜片正文 + 关联 claim（带证据徽章）
 ├─ 误区区：说法 → 纠正 → 来源
 ├─ 追问区：3–4 个可点击问题（点击打开 AI 抽屉）
 └─ 来源区：按 id 列出，含类型与等级
```

标签切换用 Client Component，默认渲染"结构之镜"，保证无 JS 时仍可读到主要内容。

### 5.3 证据分级

| 等级 | 含义 | 视觉 |
|---|---|---|
| A | 教科书级共识 | 实心徽章 + "教科书" |
| B | 综述/队列，仍在讨论 | 描边徽章 + "综述" |
| C | 传统理论（中医） | 橙色徽章 + "传统理论" |
| D | 概念类比（信息论） | 灰色徽章 + "概念类比" |

不只用颜色区分：每个徽章都有文字标签，满足色觉障碍用户需求。

### 5.4 首页首屏右侧：三维入口

模型是一个合并好的 `body.glb`（2.79 MB，443 个网格 / 579 个节点），一次加载 11 个器官，
12 个热点（肺左右各一个）用的是从模型逐个网格实测出的世界坐标，写在 `src/data/anatomy-hotspots.ts` 里，
**一个数都不要改**——改了热点就飘到身体外面。

三件必须做对、否则会静默失败的事：

1. **`model-viewer` 只能在浏览器里加载。** 它碰 `window`，服务端渲染会直接报错，
   所以放在 `"use client"` 组件里、用 `useEffect` 动态 `import()`。
2. **模型是 meshopt 压缩的，解码器要先挂上。** 必须在下发模型请求之前设好
   `ModelViewerElement.meshoptDecoderLocation = "/meshopt/meshopt_decoder.js"`。
   漏了这一步，`model-viewer` **不报错、不红屏，就是空着不出来**——这是本项目的第一号坑。
   解码器锁定 `meshoptimizer@0.24.0`：1.x 只发 ESM，而 model-viewer 用 `<script src>` 加载它，会语法报错。
3. **失败要说得出来。** 默认的空白会被当成"网卡了"。`load` / `error` 两个自定义事件都监听，
   失败时换成一句人话，并明确告诉用户"器官列表和影响链仍然可用"。

交互与降级：

- **三维不承载任何医学内容**，只回答"在哪"；点热点飞到该器官，再跳去详情页或影响链；
- 首页是完整版：11 个热点 + **按系统筛选**（内脏 / 循环 / 神经 / 淋巴，四个设计 token 上色）
  + **四个固定机位**（正面 / 右侧 / 背面 / 俯视）+ 11 个器官的快选按钮；
  快选这一排是必需的——胆在肝下面，正面视角被挡住，热点并不总是可点；
- 器官页是定位图版本（`variant="locator"`）：默认就选中该器官、镜头落位，只保留拖动，
  不给筛选和机位控件，避免和页面内容抢注意力；
- 文字先渲染，模型 `loading="lazy"`、`reveal="auto"`，不进首屏关键路径；
- `touch-action="pan-y"`，手机上拖动模型不会把页面滚动锁死；
- 热点是真正的 `<button>`，带 `aria-label` 与 `aria-pressed`，键盘可达；
- 无 WebGL、解码器 404、模型损坏时，退化成一个文字提示 + 器官列表，不白屏；
- `/chain`、`/explore` 不加载三维资源；`/organ` 只加载定位图那一个小实例。

**许可**：模型基于 Z-Anatomy（CC BY-SA 4.0）整理、几何源自 BodyParts3D（DBCLS，CC BY 4.0），
本站三维资产以 CC BY-SA 4.0 分发。页脚与 `/method` 都写了署名，完整条文见 `ATTRIBUTION.md`。

### 5.7 影响链页面（/chain）

这是本版新增的核心页面，用 SVG 而非 3D 实现，理由是：手机端 3D 体验差、加载成本高，而"链"要的是**可读**而不是**可转**。

布局分三层，由内向外：

```text

```

交互按"渐进增强"设计：

| 交互 | 行为 | 无 JS 时 |
|---|---|---|
| 点器官节点 | 高亮一阶出入边，右侧列出"影响谁/被谁影响/可能表现" | 退化为人手可读的列表页 |

| 移动端 | 图折叠为分组列表 + 迷你链 | 同左 |

表现区标题固定为「**可能相关的表现（科普参考，不用于自我判断）**」，并常驻一句"同样的表现也可能来自其他原因"。这不是免责声明，而是**交互约束**：页面任何位置都不提供"输入表现 → 推断器官"的路径。

### 5.8 关键代码结构（示意）

```ts
// src/lib/content.ts
export function validateOrgan(organ: OrganContent) {
  const claimIds = new Set(organ.claims.map((c) => c.id));
  const sourceIds = new Set(organ.sources.map((s) => s.id));

  for (const lens of Object.values(organ.lenses)) {
    for (const id of lens.claimIds) {
      if (!claimIds.has(id)) throw new Error(`missing claim ${id}`);
    }
  }
  for (const c of organ.claims) {
    if (!c.sourceIds.length) throw new Error(`claim ${c.id} has no source`);
    for (const s of c.sourceIds) {
      if (!sourceIds.has(s)) throw new Error(`missing source ${s}`);
    }
  }
}
```

## 8 创新点

### 8.1 技术创新

1. **边级证据分级的知识图谱**：证据等级不是文章级标签，而是**每一条关系**的必填字段；`caveat` 同样必填，"关联不等于因果"被写进数据结构而非页脚。
2. **图谱约束的检索增强（Graph-constrained RAG）**：模型只能使用给定子图中的边组织答案，输出的路径逐边回溯校验；模型无法"走出图外"编造关系。
3. **引用存在性校验**：AI 返回的 `sourceId` 必须命中真实数据，否则丢弃；引用为空整条回退——从工程上阻止编造引用，而不是靠提示词请求它诚实。
4. **链式三级降级**：模型不可用 → 预生成链；图渲染不可用 → 列表视图；JS 不可用 → 服务端渲染文本仍可读。
5. **红旗前置拦截**：安全逻辑位于模型之前，急症关键词不进入推理流程。
6. **构建期内容完整性检查**：claimIds / sourceIds 悬空即构建失败，把内容错误前移到 CI。

### 8.2 应用创新

1. **从"器官百科"到"影响链"**：回答"它坏了，身体会怎样"，而不是"它长什么样"；把知识从静态条目变成可走的路径。
2. **把"关联≠因果"做成界面约束**：表现区固定提示 + 边级 `caveat` + 三类关系分离，并**刻意不提供症状自查入口**。
3. **同一器官的三种读法并置**：结构、关系、信息三种视角同屏对照，而不是分成三篇文章。
4. **把"这句话有多可信"做成交互**：证据徽章常驻每条结论与每条关系旁，读者不需要滚到文末找参考文献。
5. **面向信息素养的教学设计**：方法页把分级规则公开，读者可学习"如何判断一条健康说法"。
6. **跨专业协作的产品化**：临床医学提供证据判断，信息工程提供校验机制，两套习惯被写进同一份数据结构。

### 8.3 与同类产品对比

| 维度 | 常见科普站 | 通用 AI 问答 | 人体棱镜 |
